# CLAUDE.md — «Іскра» (Spark Climb)

Цей файл Claude Code читає на початку кожної сесії. Тут коротко: що за проєкт, як працювати і які правила діють. Деталі лежать у `docs/`.

## Проєкт

Мобільна аркада для Android на Godot 4. Іскра автоматично стрибає вгору з плитки на плитку, камера постійно підіймається, знизу наступає темрява. Програш настає, коли герой опиняється нижче краю екрана.

Головна фішка — **світло як ресурс**. Світ темний, герой освітлює лише коло навколо себе. Точні («ідеальні») приземлення в центр плитки будують комбо, комбо збільшує радіус світла, а більше світла дає змогу бачити й планувати далі.

Поточна мета — **MVP** (див. `docs/ROADMAP.md`). Усе, що поза MVP, не реалізуємо без явного прохання власника.

## Технології

- **Godot 4.7.x** (стабільна гілка), стандартна збірка без .NET; мова **GDScript** зі статичною типізацією.
- Рендерер **Compatibility** (OpenGL) — найширша підтримка Android-пристроїв, підтримує 2D-світло.
- Портретна орієнтація, базова роздільна здатність **720×1280**, stretch mode `canvas_items`, aspect `keep_width`.
- Ціль: Android (APK). Розробка на macOS, тестування на фізичному Android-телефоні.
- Сторонні плагіни й аддони: **немає**. Додавати лише після погодження з власником.
- Графіка MVP: геометричні примітиви (Polygon2D, ColorRect) + 2D-світло. Жодних зовнішніх зображень, крім текстури світла та іконки.

## Команди

Аліас `godot` налаштовано за `docs/SETUP.md`.

```bash
# Імпорт ресурсів і перевірка, що проєкт завантажується без помилок скриптів
godot --headless --path . --import

# Юніт-тести чистої логіки
godot --headless --path . -s res://tests/test_runner.gd

# Запустити гру на ПК (сенсор емулюється мишею)
godot --path .
```

Запуск на телефоні робить власник через редактор (кнопка Remote Debug), див. `docs/SETUP.md`.

## Як працювати з власником (режим навчання)

Власник вчиться розробці ігор: знає Git, але вперше працює з Godot і Claude Code. Мета — не лише робоча гра, а й розуміння, як вона влаштована.

1. **План перед кодом.** Для будь-якої задачі, більшої за дрібний фікс, спершу коротко опиши план: які файли й сцени, які вузли, які сигнали. Дочекайся підтвердження.
2. **Пояснення після змін.** Після кожної задачі напиши 3–6 речень українською: що зроблено, чому саме так, які концепції Godot використано (наприклад, `CharacterBody2D`, сигнали, `@export`, Resource). Коротко і по суті.
3. **Малі кроки.** Одна задача з ROADMAP за раз. Кожен крок лишає гру в робочому стані.
4. **Дії в редакторі.** Якщо щось надійніше зробити в редакторі Godot (налаштування експорту, візуальна перевірка, складна правка сцени), дай власнику покрокову інструкцію замість здогадок.
5. **Перевірка.** Після змін запусти `--import` і тести. Скажи, що саме власник має перевірити руками: на ПК чи на телефоні, і на що дивитися.
6. **Git.** Працюй за розділом «Git-процес» нижче. Не коміть самостійно: наприкінці задачі запропонуй повідомлення коміту англійською у форматі `type: short description` (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`). Комітить власник.
7. **ROADMAP.** Коли власник прийняв задачу, познач її `[x]` у `docs/ROADMAP.md`.
8. **Неоднозначність.** Якщо специфікація неповна або суперечлива — спитай, не вигадуй. Узгоджені зміни дизайну фіксуй у відповідному документі.

## Git-процес

Кожен етап роадмапу (M0, M1, M2, …) виконується в **окремій гілці**. Головна гілка — `main`. Пуш, пул-реквести й мерж у `main` робить **лише власник**.

**Назва гілки:** `milestone/m<номер>-<коротка-назва>` англійською, наприклад `milestone/m0-setup`, `milestone/m1-player-jump`, `milestone/m2-endless-tower`.

**Перед першою задачею нового етапу** виконай перевірки по черзі й зупинись на першій, що не пройшла:

1. `git status` — робоча копія чиста. Якщо ні, повідом власника і не продовжуй.
2. `git checkout main` і `git pull` — оновити `main` з віддаленого репозиторію (якщо віддалений репозиторій ще не налаштовано, пропусти `pull` і скажи про це).
3. Переконайся, що гілка попереднього етапу вже в `main`: `git branch --merged main` має містити її.
   - Якщо гілки немає в списку, вона могла бути змержена через **squash** чи **rebase**, і Git цього не бачить. Тоді перевір `git log main --oneline` на наявність комітів попереднього етапу, покажи власнику результат і **спитай підтвердження**.
   - Якщо попередній етап не змержено — **не створюй нову гілку**. Повідом власника, що треба спершу змержити, і зупинись.
   - Для M0 цей крок пропускається.
4. `git checkout -b milestone/m<N>-<назва>` — створити нову гілку від оновленого `main`.
5. Повідом власника, яку гілку створено.

**Під час етапу** усі задачі цього етапу виконуються в його гілці. Перед кожною задачею перевір `git branch --show-current`; якщо ти не в гілці поточного етапу, зупинись і спитай.

**Заборонено без прямого прохання власника:** `git push`, `git merge`, `git rebase`, `git reset --hard`, `git branch -d/-D`, будь-які зміни в `main` (крім `git pull`), робота поза гілкою етапу.

**Кінець етапу.** Коли всі задачі етапу позначено `[x]`, нагадай власнику: закомітити, запушити гілку й змержити її в `main`. Наступний етап починається лише після цього.

## Конвенції коду

- **Коментарі в коді — англійською. Документація — українською. Тексти в інтерфейсі — українською.**
- Статична типізація скрізь: `var speed: float = 0.0`, `func jump(force: float) -> void:`.
- Іменування: файли, змінні, функції — `snake_case`; класи — `PascalCase` через `class_name`; константи — `UPPER_SNAKE_CASE`; сигнали в минулому часі (`landed`, `combo_changed`).
- **Жодних магічних чисел у геймплеї.** Усі параметри балансу живуть у `GameConfig` (`config/game_config.tres`). Нові параметри додавай туди з коментарем і значенням із `GAME_SPEC.md`.
- Сцена і її скрипт лежать поруч у теці своєї фічі (див. структуру в `ARCHITECTURE.md`).
- Зв’язок між системами — через сигнали та autoload `Events`. Не тягнися до чужих вузлів через `get_node("../../...")`.
- Чиста логіка (математика приземлення, комбо, крива складності, вибір типу плитки) лежить у `logic/` і не залежить від сцен, щоб її можна було тестувати.
- Кожен скрипт починається з doc-коментаря `##`, що описує його відповідальність.
- Функції короткі; якщо скрипт перевищує ~200 рядків — це сигнал розділити відповідальність.

## Пастки Godot 4 (не плутати з Godot 3)

- `CharacterBody2D`, а не `KinematicBody2D`; властивість `velocity`; `move_and_slide()` без аргументів.
- Анотації `@export`, `@onready`, `@export_group`; сигнали через `my_signal.connect(callable)` і `my_signal.emit(...)`.
- `.tscn` можна редагувати як текст, але обережно: зберігай коректні `ext_resource`/`sub_resource` id і `uid`. Після правок обов’язково запускай `--import`. Складні зміни сцени краще описати власнику для редактора.
- Godot 4.4+ створює файли `*.uid` поруч зі скриптами. Їх треба комітити, не видаляти й не перейменовувати вручну.
- Тека `.godot/` — кеш, не редагувати (вона в `.gitignore`).
- Класи з `class_name` стають доступними в headless-режимі лише після `--import`.
- Сенсорне введення на ПК емулюється мишею (`input_devices/pointing/emulate_touch_from_mouse`), тож драг перевіряється мишею.
